How I created server B

My servers are on Hetzner, not cPouta, so I couldn't make B from a cPouta snapshot of A. B is a separate Hetzner server with its own IP (95.216.189.103). It's not an exact copy either: A runs Ubuntu 26.04 and B runs Rocky Linux 10 (ARM). So I moved over what B needs by hand instead of cloning the disk:

  • Files and settings: the repo is cloned on both servers. The setup script for B (setup/setup-b.sh) installs nginx, MariaDB, Python and PyMySQL and copies B's configs into place.
  • Database: not copied as a dump. A had binary logging on before I created the week2 database, so B started replication from the very beginning of A's binlog and built the same database and data from it.
  • MariaDB version: Rocky's own MariaDB is 10.11, but A has 11.8, and a replica shouldn't be older than its primary. So B gets MariaDB 11.8 from MariaDB's official repository.

Users, database users and permissions

Linux users

  • kalle (A and B): my admin user. On A it runs the week 2 app, the week 3 report and the backup cron job.
  • backup (B only): receives backups. Password locked, SSH key login only. Its key in authorized_keys is forced to rrsync -wo /srv/backups/server-a with restrict, so A's key can only upload files into that one folder. It can't get a shell, read old backups or delete anything, even if A is hacked.
  • week4 (B only): system user with no login shell that runs B's page app. The systemd service also uses ProtectSystem=strict and ProtectHome=true, so the app can't write to the system.

Database users

  • week2app@localhost (A): only SELECT, UPDATE on week2.counter. Used by the week 2 app.
  • repl@95.216.189.103 (A): only REPLICATION SLAVE, can log in only from B's IP, and only over SSL.
  • week4ro@localhost (B): only SELECT on week2 plus SLAVE MONITOR to show the status above. On top of that, B runs with read_only=ON, so ordinary users can't write even if they had the grant.
  • root (both): only through sudo mariadb (unix socket), no password login.

Hourly backups

kalle's crontab on A has 5 * * * * /home/kalle/linux-week4/backup/backup.sh, so it runs at 5 past every hour. The script:

  1. packs /var/www/html and /var/www/week-1 into www-<UTC time>.tar.gz in a temp folder. (The assignment asks for /var/www/html, but my actual pages are in /var/www/week-1, so I back up both.)
  2. uploads it to backup@B with rsync over SSH, using the restricted key.
  3. writes OK or FAIL with the reason to /home/kalle/backup.log, and deletes the temp file.

On B, the backup user's own cron job (30 * * * *) deletes everything except the newest 48 archives, so there are always about 2 days of hourly versions.

Continuous replication

A is the primary. Every change to the week2 database is written to A's binary log (row format). B connects to A as repl over SSL on port 3306. Its IO thread copies new binlog events into B's relay log as soon as they happen, and its SQL thread applies them to B's own copy of the database. It uses GTIDs, so after a restart B continues from where it stopped. On A, ufw only lets B's IP connect to port 3306. On B, MariaDB only listens on localhost.

Why replication doesn't replace backups: replication copies every change right away, including mistakes. If someone runs DELETE FROM counter or the data gets corrupted on A, B gets the same damage within a second. Replication only gives you a second live copy of now. To go back to how things were yesterday you need historical backups (timestamped copies) that later changes can't touch.

Problem I solved

The first backup upload failed with Permission denied (publickey), even though the key was in /home/backup/.ssh/authorized_keys with the right permissions. B's SSH log said "User backup from 46.62.229.94 not allowed because not listed in AllowUsers": B's sshd config has AllowUsers kalle, so no other user can log in at all. I added a drop-in file /etc/ssh/sshd_config.d/50-week4-backup.conf with AllowUsers backup@46.62.229.94. AllowUsers lines add up, so kalle still works and the backup user is only allowed from A's IP.

Something I learned while testing: rrsync -wo (write-only) stops A from reading backups, but it still let my test delete one with rsync --delete. So I added -no-del -no-overwrite to the key. Now A can only add new backups, and even if A got hacked, it couldn't destroy the old ones on B.
